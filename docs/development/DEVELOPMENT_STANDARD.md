# 长任务协作与隔离开发规范

> 版本：1.0 ｜ 生效日期：2026-08-05 ｜ 适用范围：Turtle、年糕及后续采用本模板的项目

## 1. 目标

本规范解决三件事：长任务始终围绕用户目标推进；项目状态可在离开数小时后快速恢复；任何功能改动都在独立工作区和分支中完成，并以绑定当前提交的验证证据作为进入主分支的前提。

路线图、测试或审查都是服务目标的手段，不能反过来改写产品目标。新证据可以调整计划、顺序和完成证据，但改变最终目标、扩大外部影响或降低质量门必须由用户批准。

## 2. 项目状态真源

每个项目维护以下工件：

| 工件 | 作用 |
|---|---|
| `GOALS.md` | 里程碑、当前状态、决策、阻断和完成证据的协调真源 |
| 领域路线图 | 产品/技术长期真源；例如 Turtle 的 `docs/development/LONG_TERM_ROADMAP.md` |
| `progress-dashboard.html` | 只展示当前目标、完成项、下一步、阻断、最近证据和最近决策 |
| `.project-governance.json` | 受保护分支、允许的分支前缀和验证档配置 |
| `project_guard.py` | 创建 worktree、前置检查、运行验证和检查合入资格 |
| `.project/evidence/latest.json` | 最近一次验证证据；必须绑定分支与 commit，不进入版本库 |

`GOALS.md`不复制领域路线图全文。领域路线图回答“系统要建成什么”，`GOALS.md`回答“当前里程碑如何协调并用什么证据结束”。冲突时先审计并显式修正文档，禁止静默选择对实现更方便的一份。

## 3. 角色与线程

主线程是协调者，只保留会影响项目方向的信息：目标、约束、重要决策、当前状态、证据和下一步。实现细节留在代码、测试日志、子任务或独立线程中。

执行任务返回四项即可：结论、实际改动、验证证据、建议下一步。不要把完整探索流水账复制回主线程。

以下工作优先放入可独立检查的线程：

- 里程碑末尾的路线图审计；
- `/review`或等价代码审查；
- 需要反复回看的架构调查；
- 依赖登录态、桌面权限、模拟器或真机的本地验证。

有界、一次性且不需要可见历史的任务可以交给子代理。是否并行不能削弱主线程对结果、证据和合并资格的最终判断。

## 4. Goal 与里程碑生命周期

同一线程只维护一个活动 Goal，且必须对应 `GOALS.md` 中一个 `IN_PROGRESS` 或 `VALIDATING` 里程碑。Goal 写结果，不写实现清单，并明确完成所需证据。

里程碑状态为：

```text
PLANNED → IN_PROGRESS → VALIDATING → COMPLETE
                         ↘ BLOCKED
```

只有实际阻断且无法继续时才标记 `BLOCKED`。发现新信息后允许修改范围、顺序或证据，但必须在 `GOALS.md` 的决策记录中说明原因。

里程碑结束顺序固定为：

1. 实现者提交改动和证据。
2. 独立审计路线图与当前代码，确认完成定义仍成立。
3. 独立代码审查处理正确性、回归和安全问题。
4. 补齐真实环境或 Computer Use 验证。
5. 更新 `GOALS.md` 与状态面板。
6. 当前 Goal 完成后，才激活下一个 Goal。

## 5. 强制隔离开发

### 5.1 基本规则

- `main`和`master`只用于已验收代码，不作为日常开发目录。
- 每项改动使用新的 linked worktree 和新的功能分支。
- 分支必须使用 `feat/`、`fix/`、`docs/`、`refactor/`、`test/`、`chore/`或`hotfix/`前缀。
- 一个 worktree 只服务一个明确目标；不得把不相关修复混入同一分支。
- 禁止在主工作区直接提交；禁止绕过失败测试合入主分支。

从干净的主工作区启动：

```bash
python3 scripts/project_guard.py start fix example-slug
```

Android 年糕使用：

```bash
python3 tools/project_guard.py start fix example-slug
```

工具默认在仓库同级的 `worktrees/<repo>/` 下创建 linked worktree，并从 `main` 建立分支。主工作区不干净时工具必须停止，因为此时从 HEAD 建出的新空间不会包含未提交基线。如果根仓库存在被忽略的 `.venv/`，`start` 会在新 worktree 建立指向它的本地 symlink，并写入仓库本地的 Git `info/exclude`；虚拟环境不会进入提交，也不会让工作树被误判为 dirty。

### 5.2 当前脏主干的迁移规则

引入本规范时已经存在于主工作区的未提交改动属于“历史基线”，不得假装已经进入新流程，也不得自动 stash、reset 或批量搬运。必须先：

1. 盘点改动来源和范围；
2. 运行当时适用的完整验证；
3. 建立可恢复快照或基线提交；
4. 经用户确认后结束一次性迁移；
5. 从此不再向主工作区加入功能改动。

这是一项明确阻断：基线未冻结前，可以完善治理文档和只读审计，但不得声称新 worktree 流程已经覆盖历史改动。

## 6. 提交与合入门禁

本地 hook 通过 `core.hooksPath=.githooks` 启用：

- `pre-commit`检查当前不是受保护分支、分支名合规且目录是 linked worktree；
- `pre-push`阻止直接推送 `main/master`；远端主分支应只接受 PR 或受控合并。

开发完成后先提交，再运行验证。验证要求工作树干净：

```bash
python3 scripts/project_guard.py verify full
python3 scripts/project_guard.py merge-check
```

年糕使用 `tools/project_guard.py`。`verify`生成的证据绑定当前分支和 HEAD commit；提交发生变化后旧证据自动失效。`merge-check`只有在以下条件同时满足时通过：

- 位于合规的独立 worktree 和功能分支；
- 工作树干净；
- 验证成功；
- 验证证据与当前分支、当前 commit 完全一致；
- 验证档达到项目配置要求。

通过门禁只是“可以申请合入”，不是自动授权合并。仍需完成路线图审计、代码审查和项目要求的人工/真机验收。

Turtle 仓库提供 `.github/workflows/change-gate.yml` 作为 PR 回归检查。工作流文件本身不会自动开启 GitHub branch protection；远端仍需把该检查设为 required，并禁止绕过 PR。该外部设置必须在获得授权后执行。

## 7. 项目验证档

### Turtle

- `docs`：治理配置和工具自检；只适用于文档草稿检查。
- `fast`：核心配置与派生指标定向回归。
- `full`：全部阶段回归及 completion/auto-repair 契约测试；领域文档要求的其他定向测试、真实样本、validation-only和昂贵运行授权仍额外生效。

### 年糕 Android

- `docs`：治理配置和工具自检。
- `fast`：`:app:testDebugUnitTest`。
- `full`：单元测试、`:app:lintDebug`和`:app:assembleDebug`。
- Room 变更仍必须核对迁移和导出 schema；备份恢复、权限、行情和关键交易交互必须补真机或模拟器证据。

文档变更可以用较低验证档迭代，但进入 `main` 的默认最低门槛仍是项目配置的 `full`。若某类纯文档变更确需降低门槛，应修改治理配置并记录决策，而不是临时跳过。

## 8. 审查、Computer Use 与发布

单元测试无法替代真实交互。涉及浏览器登录、桌面权限、Android 真机/模拟器、备份恢复或外部凭证时，在独立本地线程验证正确 commit，并返回截图、日志、设备/系统版本和复现步骤。

代码审查至少检查：需求是否满足、业务真源是否一致、迁移/兼容路径、失败恢复、测试是否覆盖错误路径、是否混入无关改动。路线图审计则检查：里程碑是否真的结束、下一个目标是否仍正确、是否出现遗漏里程碑或失效的完成定义。

发布、昂贵真实运行、外部消息、远端配置和主分支保护属于独立授权边界。通过本地测试不自动授权这些外部动作。

## 9. 状态汇报

项目状态发生变化时只报告：

```text
已完成
下一步
阻断项
```

每项附最短可核验证据，例如测试命令、commit、报告指纹或设备截图。没有阻断时写“无”，不要用候选动作或中间判断要求用户逐步审批。

## 10. 在其他项目快速部署

使用仓库内 `codex-skills/orchestrate-projects`：

```text
使用 $orchestrate-projects 为当前仓库建立长任务治理，项目名为 <name>，类型为 python/android/generic。
```

技能会生成 `GOALS.md`、开发规范、治理配置、状态面板、门禁工具和 hooks。部署后必须根据项目调整验证命令，执行工具自检，并在启用 hooks 前处理已有脏主干。远端仓库还应把 `main`设置为受保护分支，要求 PR、至少一项独立审查和对应的 required checks。

## 11. 例外

紧急修复仍使用 `hotfix/` linked worktree，不能直接在 `main`修改。唯一允许绕过本地受保护分支推送 hook 的环境变量是 `PROJECT_ALLOW_PROTECTED_PUSH=1`，仅供已记录、已验证且无法使用远端合并机制的受控操作；使用后必须补写决策、证据和复盘。它不能绕过测试失败或替代用户批准。
