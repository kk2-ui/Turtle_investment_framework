# R-36：明源云 2021–2022 云客：行业状态打断产品指标的边界复验

**状态**：`RESULT_KNOWN_TEACHING / BOUNDARY_REPLICATION / MIXED_OPERATING_SIGNAL / NO_CAPABILITY_OR_OWNER_CASH_CONCLUSION / NO_TURTLE_BACKTEST`

**本卡训练的问题**：在客户行业需求急转弱时，一家企业为提高获客和成交效率而追加产品功能，客户覆盖、留存和单客户收入出现相反方向时，怎样避免把其中任一指标单独写成产品价值、定价权或能力结论？

R-36 是 R-35 的**边界复验**，不是 near miss：两者的客户类型、收入/定价机制、外部冲击和产品边界不同。它只测试同一条更高层纪律——价格/ARPU、客户留存和行业状态必须一起解释。

## 1. 状态、压力与实际选择

| 项目 | 当期事实 | 可训练的含义 |
|---|---|---|
| S5 状态变化 | 2021年下半年房地产开发商面对销售/营销压力。 | 行业客户的预算、项目数量和数字化需求不再能用“软件产品自身增长”概括。 |
| 实际选择 | 公司表示推出智慧销讲、智慧工牌等应用，目标是加强购房者、置业顾问、第三方销售代理和经纪人的互动，改善客户体验、提升开发商获客及成交转化效率。 | 这是在客户压力下的具体产品/资源响应；不是已经证明其解决了开发商的经济问题。 |
| 经营替代 | 保持原有 CRM Cloud 功能与销售资源，避免在行业需求恶化时继续投入；或把资源转向不同客户/产品线。 | 这是基于已披露行动形成的经营替代，不是公司管理层披露的反事实。 |

行动来源：[明源云2021年报](https://www.mingyuanyun.com/Public/Uploads/uploadfile/files/20240817/MingYuanCloud2021AnnualReport.pdf)。它同一报告还披露：2021年配置 CRM Cloud 的国内售楼处约16,600个，CRM Cloud 年度客户账户留存率为88%（2020年90%）。

## 2. 竞争机制叉

| 机制 | 传导 | 需要的区分观察 |
|---|---|---|
| H-A：产品响应提高客户经营效率 | 新功能在需求收缩时仍提升开发商获客/转化，故同口径客户覆盖/留存至少稳定，且单售楼处收入的提高不是靠被动提价或客户收缩。 | 同一客户 cohort 的产品使用、续约、价格/折扣与服务成本；在行业状态控制下的客户结果。 |
| H-B：行业收缩/客户构成主导 | 新功能是防御性应对；项目数/客户预算收缩压低覆盖和留存，较高单客户收入可以来自保留客户构成、收费或服务组合，不能证明效果。 | 覆盖、留存和 ARPU 的联合方向，以及产品/客户构成与行业需求的拆分。 |

## 3. 已知结果：只能得到“混合信号”

2022 年报在同一 CRM Cloud 产品名下披露：配置该产品的国内售楼处约12,278个，较2021年约16,600个下降约26%；单售楼处平均收入74,400元，同比提高20.4%；客户账户留存率82%，低于2021年的88%。[明源云2022年报](https://www.mingyuanyun.com/Public/Uploads/uploadfile/files/20240817/MingYuanCloud2022AnnualReport.pdf)

因此可机械写为：

```text
客户覆盖 ↓；客户账户留存 ↓；单售楼处收入 ↑
→ 不是 H-A 的单向支持，也不是“ARPU提高=产品价值提高”
→ MIXED / 环境与构成仍未拆开
```

这是比“收入增长/下降”更有价值的反例：同一个产品在行业状态转换后，ARPU 与覆盖/留存可以给出相反信息。它要求研究者回到客户身份、合同、价格、使用、成本和外部需求，而非选择最漂亮的一项 KPI。

## 4. 仍不能回答的事

| 不可越过的结论 | 缺失原因 |
|---|---|
| 新功能没有价值或造成留存下降 | 2022 的行业需求、开发商预算、项目开工/销售、客户构成和收费调整没有被分离；没有处理/对照客户。 |
| ARPU 上升证明定价权/客户价值 | 未披露同 cohort 的价格、折扣、使用深度、客户利润或新旧客户构成。 |
| 云客产品经济或 owner cash 恶化/改善 | 没有云客单品的交付、服务、获客现金和资本占用；公司 SaaS/ERP/其他产品不能替代。 |
| 公司已经证明反馈学习能力 | 虽有“压力 → 新功能”行动，但没有逐项客户反馈、资源取舍和独立第二条经济链。 |

## 5. 对飞轮的更新

R-35 的变量收费案例与本卡共同留下一个状态条件：

```text
ARPU / product gross margin
必须同时读取
customer cohort retention + customer/usage coverage + state-specific external demand
否则只允许 PRODUCT_MONETIZATION_MECHANICS_OBSERVED 或 MIXED。
```

这不是要求为所有公司建立宏观模型；而是要求行业专家视角明确指出：哪个外部状态能使“产品收入/ARPU”与“客户留存/覆盖”分叉。经营者视角则要求写出仍可选择的资源动作；所有者视角只能在产品现金边界真实可见时再介入。

## 6. 审阅结论

**根因分类**：`DATA_COVERAGE + REASONING`。公开材料能确认行动以及覆盖、留存、ARPU的方向，却没有让研究者识别产品效果、客户构成与房地产周期各自的贡献。若从其中单取 ARPU 或保留率，会误判产品持续性、正常盈利和资本回报。

**禁止假设**：功能发布必然提高客户留存；ARPU提高必然等于定价权；客户数下降必然等于产品失败；行业下行自动否定产品价值；公司 SaaS 合并毛利/OCF 等于云客现金。

**接纳标准**：本卡只作为 `STATE_CONDITIONED_METRIC_DIVERGENCE` 的历史教学案例保留。后续任何“客户经营/数字化”案例须预先写出覆盖、留存、ARPU 的联合方向及行业状态代理；若无同 cohort 的价格、使用、成本和合同现金，不得裁决产品经济、能力或 owner cash。
