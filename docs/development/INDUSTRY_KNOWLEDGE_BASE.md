# Turtle 行业机制知识库

> 状态：ACTIVE
>
> 定位：正式、可追溯的 Turtle 基础设施。它沉淀可复用的行业机制，帮助下一份研究提出正确的问题；它不是 Tencent 对话记忆、公司研究缓存、案例概率库，也不是估值参数库。
>
> 2026-08-19 路线路由：`GOLDEN_REPORT_BIDIRECTIONAL_RESEARCH_ROADMAP.md` 规定 G1.5 先完成并接纳公司—时点黄金报告，再形成行业综合和机制候选。机制卡、案例卡、驱动树或摘要不得替代任何一份黄金报告；报告接纳也不自动把机制升格为 `MECHANISM_READY`。
>
> 2026-08-20 资产复用裁决：`config/insight_case_benchmark.json` 的方法卡和 `output/.base_rate_library/` 的基准率候选已经存在，不得在 G1.5 重复建设；前者含 4 个具名书中案例与 4 个 Turtle 综合研究原型，分别负责研究动作校准和预测结果积累，均不等于行业机制卡，也不计入 24 份黄金级产物。

## 1. 要解决的问题

读完一份完整报告后，研究者往往得到有价值的解释，例如“装瓶商的毛利改善可能被渠道费用抵消”或“物业城市服务的应收与启动资金通常高于住宅物业”。如果这些解释只留在单份报告或对话上下文中，下一家公司又会从零开始；如果把它们直接当成新公司的事实，又会把类比误写为证据。

行业机制知识库解决前者，同时禁止后者。它保存的是经过跨公司、跨期间检验的机制卡，供研究流程检索、提出待核验问题、发现反例和安排取证。每一家公司仍须用自己的公告、年报、监管文件或其他一手来源完成验证。

## 2. 四层职责，不可互换

| 层 | 保存什么 | 能做什么 | 明确不能做什么 |
| --- | --- | --- | --- |
| 官方证据与公司研究底稿 | 本公司披露、数据、观察和计算 | 支撑公司主张、模型输入和投资结论 | 不能因一家公司而宣布行业规律 |
| 行业机制知识库 | 多公司、多期间检验后的机制、适用边界、反例和证据指针 | 生成问题、列出应取字段、提供竞争解释和反例 | 不能直接生成公司事实、估值、买卖动作或概率 |
| 基准率案例库 | 事前预测、事后结果和资格审阅 | 在同机制且至少五个 `ELIGIBLE` 案例时计算经验频率 | 不能当行业知识卡、不能代替公司证据 |
| Tencent Memory / company context | 会话续跑提示、已发布对象的导航摘要和指针 | 找到 canonical 机制卡或公司对象 | 不能作研究证据、估值输入、概率或结论依据 |

四层之间允许传递的是**可回溯指针**，不是事实复制。报告中任何材料数字、公司事实、模型参数和主张，仍须回到本公司可审阅证据或确定性计算。

### 2.1 三类“案例”对象的身份

| 对象 | 回答的问题 | 当前入口 | 与行业机制库的关系 |
|---|---|---|---|
| 方法案例卡 | 这类公司最该先判断什么、禁止走什么捷径；`NAMED_BOOK_CASE` 与 `SYNTHESIS_PATTERN` 来源身份显式区分 | `config/insight_case_benchmark.json` | 只生成研究挑战问题，不构成机制证据、公司 episode 或经验频率 |
| 基准率案例 | 当时作了什么预测，后来结果如何 | `output/.base_rate_library/` | 合格结果可形成经验先验，但不能直接升格机制或替代公司证据 |
| 公司—时点黄金报告 | 该公司在特定信息集下的完整事实、判断、模型与结论 | G1/G1.5 案例包 | 多报告可提出机制候选；仍须跨公司、跨期、反例和独立审阅 |

从黄金报告派生的“案例索引”只能链接上述对象，不得复制出第二份事实、预测或结果真源。现有方法案例卡已经完成的决定性问题、必做研究动作和禁止捷径应直接复用；现有基准率 `CANDIDATE` 应按原 cutoff、到期日和追加式事件继续成熟，而不是重新抽取成新 ID。

## 3. 洞察候选、机制卡与公司验证状态

每张机制卡以稳定的 `mechanism_key` 标识，至少包含：

- 一句可证伪的机制陈述，而不是“行业景气”这类标签；
- 适用的商业原型、地理/监管范围、时间范围和前置条件；
- 正向证据与反例，各自保留公司、`corporate_group_id`、报告期、披露时间和来源指针；
- 机制成立时应在公司披露中寻找的字段、方向和观察窗口；
- 竞争解释、失效条件与不适用边界；
- 已知数据缺口和最近复核时间。

公司洞察候选和跨公司机制卡是不同对象，状态也不能混用：

| 状态 | 含义 | 检索行为 |
| --- | --- | --- |
| 洞察候选 `PROPOSED` | 从一份报告、研究笔记或人工观察提出的假说 | 不进入默认检索；只供继续取证 |
| 洞察候选 `CANDIDATE` | 有本公司直接证据，机制表述和取证字段完整 | 不进入默认检索；可被机制审阅收集 |
| 洞察候选 `REJECTED` | 证据不可回溯、机制表述不成立或不应跨公司迁移 | 不进入默认检索；保留拒绝理由以避免重复提出 |
| 机制卡 `CANDIDATE` | 已聚合候选，但独立证据不足 | 不进入默认检索；只供编辑者继续取证 |
| 机制卡 `CORROBORATED` | 至少有两个独立公司集团的佐证；只有行业确实高度集中时，才可用三个独立报告期替代，但必须标记外部有效性限制 | 不自动注入任何新报告；只供审阅者检查 |
| 机制卡 `MECHANISM_READY` | `CORROBORATED`基础上，经独立审阅逐项确认适用边界、反例、替代解释和证据清单 | 默认可以返回为研究问题与取证清单 |
| 机制卡 `RETIRED` | 反例、监管变化或后续证据已削弱机制，不能再作为默认先验 | 默认不返回；仅在历史审阅或显式要求时返回 |
| 机制卡 `REJECTED` | 跨公司机制陈述不成立或无法满足升格契约 | 默认不返回；保留拒绝理由以避免重复提出 |

`MECHANISM_READY`不代表“对所有公司都是真的”，更不代表“可以填入模型”。它只表示这是一条值得优先验证的、边界已说明的研究机制。`CORROBORATED`也不自动注入公司上下文、报告提示词、claim ledger、估值模型或概率账本；只有在新公司完成一手证据验证后，才可作为该公司研究任务的背景线索。

## 4. 升格与独立性契约

一份公司报告只能创建或补充 `PROPOSED` / `CANDIDATE` 洞察。它永远不能单独把一条机制升格为 `MECHANISM_READY`。

机制升格至少须满足以下全部条件：

1. `CORROBORATED` 默认至少有两个不同 `corporate_group_id` 的直接佐证。行业确实高度集中、无法合理取得第二公司时，才可改用三个独立报告期；该例外必须有清楚的集中度事实和`external_validity_limited`标识，不能把它伪装成跨公司验证。
2. 同一控股集团、同一合并范围、同一资产平台或同一实际控制人不得计为独立公司；把同一期年报、业绩会、新闻稿或转载拆成多条记录也不能伪造跨期验证。每项用于计数的证据均须保留 `corporate_group_id`、报告期、`source_group_id`、披露时间和一手来源指针。
3. `MECHANISM_READY` 不能按候选数量自动升级。除合格的 `CORROBORATED` 证据外，独立审阅者还必须逐项批准机制陈述、适用条件、不适用条件、至少一个反例或失败路径、替代解释及本公司必取字段。机制作者身份与审阅者身份必须分开；同一人不得以自己的结论完成独立升格。
4. 没有反例并不自动否定机制，但必须明确写出已经检索的范围和仍未知的边界。

跨期数据的作用是检查机制是否可能只是短期噪声；跨公司数据的作用是防止把公司特有的资本结构、客户关系或会计选择误称为行业规律。二者不可互相替代。

## 5. 新公司研究时的正确用法

检索机制卡后，系统应返回的是“待验证问题包”，而不是结论。一个返回项目至少含：

```text
mechanism_key
机制可能怎样影响利润、现金或风险
本公司必须补取的字段和一手来源位置
成立与不成立分别会看到什么信号
反例与不适用条件
本公司当前证据状态：SUPPORTED / NOT_EVIDENCED / CONTRADICTED / NOT_APPLICABLE
```

当机制与新公司原型匹配、但尚无本公司一手证据时，状态必须是 `NOT_EVIDENCED`。它只会新增决定性问题或研究任务，例如“查明渠道费用率是否抵消毛利变化”，而不能写成“该公司毛利改善将被渠道费用抵消”。

`NOT_EVIDENCED`也不能改善信心、降低要求回报、提高买入价格，或作为反方已被证伪的理由。只有本公司证据完成后，研究者才能在公司账本中形成独立的 `SUPPORTED`、`CONTRADICTED` 或 `NOT_APPLICABLE` 判断。

## 6. 估值、主张和概率的隔离

行业机制卡不是模型输入。以下路径一律禁止：

```text
机制卡 -> 估值参数 / 目标价 / 回报率
机制卡 -> 公司事实主张
机制卡 -> 情景概率或置信度
机制卡 -> 买入、卖出、仓位动作
```

允许的路径只有：

```text
机制卡
-> 提出本公司待验证问题和字段
-> 取得本公司 VERIFIED 证据
-> 公司层面的事实、判断、模型与敏感性
-> 独立审阅后的估值或决策
```

经验概率属于另一条受控路径：只能来自基准率案例库中同机制、独立审阅后且至少五个 `ELIGIBLE` 案例；即使有足够样本，它也只是先验，必须与本公司证据分开呈现。机制卡本身既不能提供概率，也不能借用案例数伪造公司证据。

## 7. 反例、退役与时间边界

机制卡必须保存与正向证据同等可见的反例。反例可能表明机制仅适用于某种区域、监管框架、资产期限、客户结构或资本结构；也可能要求缩小机制的适用范围。

若后续反例、制度变化或独立审阅否定了卡片的核心陈述，应将卡片标为 `RETIRED`，保留历史与退役理由。默认检索不得返回 `RETIRED` 卡，也不得把它作为当前研究先验。显式历史审阅可以返回它，但必须同时显示退役原因和替代卡（如有）。

## 8. Tencent Memory 的受限接缝

Tencent Memory 只可保存机制卡的导航摘要，例如 `mechanism_key`、标题、版本、状态和 canonical 路径。它不复制证据正文、公司数字、估值、价格、概率或结论。

Memory 不可达、过期或返回空结果时，行业知识库查询必须继续从本地 canonical store 完成；最多产生非阻断诊断。Memory 是加速导航的便利层，不是运行依赖，也不是故障时的事实备份。

## 9. 运行流程

```text
官方披露 / 监管资料
  -> 书籍方法案例卡提出研究挑战（非证据）
  -> 公司洞察候选（公司层，不能自动升格）
  -> 冻结前瞻判断；历史对象通过追加事件结算
  -> 跨公司验证，或有外部有效性限制的集中行业跨期例外 + 反例审阅
  -> MECHANISM_READY 行业机制卡
  -> 新公司的问题包（默认 NOT_EVIDENCED）
  -> 本公司一手证据验证
  -> 公司账本、模型、报告与独立复核
```

读取行业知识库前，研究流程应先读取公司当前的官方证据和原型。知识库结果用于补全“还需要知道什么”，不取代“已知什么”。写作阶段必须明示本公司证据状态，不能把机制卡内容伪装成年报事实。

## 10. 验收标准

实现完成后，自动验收至少覆盖：

| 场景 | 必须结果 |
| --- | --- |
| 单一公司的一条洞察 | 保持 `PROPOSED` 或 `CANDIDATE`，不可升格 |
| 同集团两个上市主体 | 只算一个独立 `corporate_group_id` |
| 同一集团同一报告期的多份资料 | 只算一个公司/期间证据单位，不能伪造跨期或跨公司验证 |
| 原型匹配但本公司尚无证据 | 返回 `NOT_EVIDENCED` 问题包，不产生主张/估值/概率 |
| 尝试把机制 ID 写入 valuation、claim 或 probability 输入 | 验证失败并指出禁止路径 |
| `RETIRED` 卡 | 默认查询为空，不可作为默认建议 |
| Tencent Memory 报错或缺席 | canonical 查询仍完成，状态为非阻断诊断 |
| 基准率案例库 | 只返回统计样本和先验，不改变机制卡或公司证据状态 |
